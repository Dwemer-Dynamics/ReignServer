# Correspondence options and contact priority

Control Center → Options → Correspondence provides two server-wide settings:

- `correspondenceFrequencyMultiplier`: 0–5 in steps of 0.25; default 1. Scales the sender-to-player affinity chance, rounded to the nearest whole percent and capped at 100%. Zero stops automatic personal letters and introductions before checks or generation. Known +10 and unmet +20 eligibility, three-day checks, one introduction per three days, and successful-sender 3–15-day cooldowns remain. Replies and event-triggered letters use their existing triggers.
- `correspondenceTravelTimeMultiplier`: 0.25–4 in steps of 0.25; default 1. Applies to the current quarter-time courier policy when dispatching a new letter. A current 18-hour journey takes 9 hours at 0.5×. Command reports remain immediate. Existing in-transit delivery dates and replayed dispatches remain fixed. Replies use the parent's unscaled route estimate and the current setting once; version-one parents retain their saved route estimate.

The page shows live chance examples at +20/+50/+100 affinity and three journey examples. Values save through the section button or global Save Changes. Updates are partial and validated before persistence; malformed/nonfinite/out-of-range settings are rejected. The public gameplay-options projection contains only these two numeric values alongside existing safe options. No provider credentials are exposed. Changing frequency does not reroll an already evaluated slot; a triggered check retains its recorded chance.

The native contact rail orders unread delivered incoming letters first, any visible correspondence history second (including read incoming and outgoing letters), and remaining eligible contacts last. Names sort alphabetically within each group, with character ID breaking equal-name ties. Reading the final unread letter moves that contact into the history group while retaining the selected contact object.

`/correspondence/threads` returns complete per-contact `contactStates` summaries and a bounded snapshot of the latest 1,000 visible bodies. `summaryOnly: true` returns no bodies; the native screen uses this on opening and then requests only the selected correspondent. `correspondentId` scopes bodies to the selected character; summaries continue covering all allowed contacts. Both SQL queries explicitly project their required columns. The display projection includes identity, body, status/source/reason and dispatch/delivery/delivered/read dates; private generation profiles, prompts and action diagnostics in `payload_json` never leave the ledger through this endpoint. Incoming in-transit mail remains hidden, including from summaries; other players' mail remains excluded. Existing contact eligibility/source exceptions continue. Very long individual threads retain the 1,000-body display limit; their full unread counts and history remain in summaries.

`/correspondence/read` retains the legacy single `letterId` form and accepts a batch of up to 1,000 distinct `letterIds` with required `playerId`. Batch updates affect only delivered incoming letters for that recipient; retries preserve the original read day, hidden in-transit and foreign mail stay unchanged, and stored payloads remain intact. The screen acknowledges the displayed unread letters in one request, updates their existing speaker/status labels, and sorts the existing contact widgets with a native Sorted notification. It does not rebuild the body list after acknowledgments. Cancel invalidates pending loads immediately while native layer removal stays deferred to the safe application tick. Opening explicitly binds the instantiated reply editor to its registered action composer. Offline input fixtures cannot certify native focus or frame latency; those require the deployed in-game acceptance pass.
