# Conversation intoxication and action text

## Current private action system (2026-10-08)

The ordinary response carries freely authored `reply` prose and a private `drinkActions` array. This is the sole accounting authority for new turns. The server does not search prose for sips, require a stock action sentence, compare exact quotes, or fall back to `drinkingEvents`, `drinkConsumptions` or `drinkSceneUpdates`. Older fields remain compatible schema fields and historical test fixtures, but live accounting ignores them. Historical receipts and counters are never backfilled.

Actions have a response-local `id`, `operation` (`consume/establish/refill/transfer/discard`), `holderHeroId`, `vesselId`, advisory `contentsVersion`, `beverage`, `kind`, `quantity`, `serving`, `count` and `completed`. At most 16 completed actions run in listed order. A sip and its swallowing share one action; separate sips use separate ids. Duplicate ids apply once; missing ids receive a deterministic local hash. Only the speaking NPC consumes. Environmental service can establish separate cups for present recipients. Offers and other participants never force drinking. The model sends `[]` for no action, intentions, refusals, history and hypotheticals; no automatic drinking occurs between turns.

The engine classifies beverages with `reign-beverages-v1`. An explicitly identified wine sip counts despite missing cup bookkeeping. An omitted beverage can reuse known contents. Explicitly unknown contents cannot borrow old wine identity; unresolved refills clear prior classification. A changed explicit identity invalidates the old liquid's measured remainder, with a diagnostic. Known empty cups and custody remain enforced locally. Unknown contents record an event with zero attributed alcohol and incomplete accounting, never invented alcohol strength. Portions are gameplay estimates: `sip=.25`, `half=.5`, `drink=1`; counts are bounded to 20. `finish` uses known remainder, otherwise a diagnostic quarter-serving estimate. Ordinary cups can establish full/half/quarter/empty volume; bulk capacity stays unknown. Refills increment revisions, transfers retain identity/remainder and discards remove the exact cup. Physical anchors, one-hour expiry, departure and snapshot persistence remain in effect.

Drink problems produce bounded diagnostics and local arithmetic, never a drink-specific reply rejection, repair prompt, retry, classifier or extra LLM call. Missing/malformed actions mean no unrecorded dose; valid siblings still apply. Old cup revisions are advisory. Visible narration is returned unchanged, including at tolerance. The engine caps alcohol and suppresses executable commitments; the prompt asks the character to express impairment/refusal in their own voice. Tolerance remains `max(5, native Endurance * 2)`, recovery one serving per two campaign hours, and alcohol stays blocked until below half tolerance. General provider capacity, infrastructure, negotiation and campaign-restore integrity retain their existing boundaries.

Preview prepares a receipt without saving it. Final acceptance reruns the bounded reducer against current state and inventory under row locks in the accepted-dialogue transaction. Concurrently changed state or a changed private array is locally rebased without another model decision. Final prose changes do not recount or invalidate private actions. Silent/failed responses discard effects; a failed unrelated repair clears `drinkActions`. Replayed hero/timeline/turn receipts never dose again. Receipts retain their schema and add `accountingMode=private_actions_v1`, `actionMetadataHash`, action/event ids, diagnostics, proposed/accepted amounts, `additionalProviderCalls=0`, `dialogueBlocked=false` and optional `locallyRebased`.

Run the exact validated Release artifact's `conversation_intoxication` suite for `private_drink_*`, and `prompt_efficiency` for schemas, repair retention, accepted-unit individual/group rollback/replay and the unchanged independent 6,144-token allowance. Fixtures use only run-owned `private_drink_test_`/`accepted_unit_test_` campaigns with exact cleanup. Expressive Arytha examples carry explicit fixture actions: they prove deterministic engine behavior, not live provider compliance. Provider action quality, character naturalness, native scene anchors and real save/reload remain separate acceptance. Deployment is held for this implementation.

## Historical accounting and repair record

The following sections preserve earlier implementations/evidence. Their narration/quote binding, hidden-choice precedence, exact revision rejection and canned threshold replies are superseded for new turns by `private_actions_v1` above. They remain historical contracts, not the live action reducer.

Accepted-response staging (2026-09-28): individual and shared group/event dialogue calculate intoxication without saving the draft's consumption. After later prose changes, the server checks the final narrated actions again and commits drinking together with the final negotiation decision. Removing a sip from accepted narration removes that proposed consumption. A concurrently changed drink state or restored campaign rejects the prepared effects. This adds no provider call and does not alter tolerance/recovery thresholds. Canonical receipts expose `commitState` and `acceptedReplyHash`; a preview is not consumed alcohol. Other conversation storage and native save acceptance remain separate stages.

NPC tolerance is `max(5, Endurance * 2.0)` serious-drink equivalents. At 50% the character is very intoxicated; 75% is severe; 100% is overwhelmed, sick and intermittently conscious. The server suppresses sustained replies and actionable commitments at 100%, rejects further alcohol, and retains the alcohol restriction until recovery below 50%. Recovery removes one equivalent per two campaign hours, never per chat turn. Only the native attributes.endurance value (or its native sourceFacts copy) supplies tolerance; Athletics and constructed traits never supply it. Absent attribute data uses the minimum.

Individual dialogue and the shared Party Chat/Castle Chat/social-event route append authoritative physical state after prompt compaction. Only the speaking NPC's completed consumption in accepted narration or its validated hidden choice is eligible. Offers, refusals, preparations, quoted/reported speech, historical events and other actors never establish consumption. This accounting does not constrain invented backstory, embellishment or in-character self-correction.

## Beverage and action contract (2026-09-15)

`ConversationBeverages.cs` owns the versioned `reign-beverages-v1` catalogue. It records native/Reign provenance separately from compatibility vocabulary: beer/ale, wine/hippocras, mead/honey wine, kumis/koumiss/airag/fermented mare's milk, fruit wines/cider/perry and legacy spirits. Kvass and boza require an explicitly alcoholic preparation; ordinary milk, water, tea, sherbet, vinegar and alcohol-free variants stay nonalcoholic. Availability remains a scene decision. This catalogue does not introduce items, prescribe regional customs or guess alcohol strengths.

The consumed object controls identity. Watered wine and tea mixed with brandy contain alcohol; water beside wine does not. A fictional name can identify a drink when the action defines its preparation. An unknown name or unknown variant does not become alcoholic merely because the model sends `alcohol:true`. Current accepted vessel context, an unambiguous beverage elsewhere in the same accepted action, or an unambiguous current sharing/drinking fact may resolve a generic cup. An explicit present player offer may supply beverage identity only when the NPC's accepted reply takes that offered vessel and narrates actual consumption. Historical, hypothetical, negated and multi-beverage offers do not establish contents.

The response supplies `drinkingEvents` with `actionIndex` among **all** asterisk actions, an exact complete `actionQuote`, `occurrenceIndex` among this NPC's consumptions in that paragraph, optional `evidenceQuote`, `serving` (`drink`, `half`, `sip`), integer `count`, `completed` and `alcohol`. The server independently extracts consumption occurrences. A unique exact quote repairs a wrong paragraph index. A uniquely contained evidence span may bind after harmless punctuation or clause-boundary variation; ambiguous spans still fail closed. Legacy index-only entries may bind to one uniquely matching consumption. Ambiguous/deleted metadata is never retargeted by guesswork; independently verifiable final narration can still count. Taking a mouthful and swallowing it, including a following “swallows hard,” is one occurrence; two distinct sips are two.

## Amounts and vessels

Explicit narrated quantity wins. Sip, mouthful, pull, swig, gulp and draught default to 0.25; half a cup is 0.5, half a mouthful is 0.125, a full ordinary cup is 1. The generic phrase “a drink” leaves amount open to compatible bounded model metadata and otherwise uses the quarter-serving fallback; “a full drink” remains 1. Explicit positive counts are bounded at 20 per occurrence. Invalid/exaggerated metadata cannot increase an explicit quantity or erase otherwise established consumption. No strength/ABV recalibration is included.

One unambiguous vessel is retained per NPC in the current conversation/location, for at most one campaign hour without a new accepted observation. A null remaining volume means unknown. Explicit refills, including a picked-up “refilled” or “freshly filled” ordinary vessel, establish one-serving volume; pouring an unspecified amount leaves volume unknown. Bottles/jugs do not acquire an assumed one-serving capacity. Sips decrement known volume; finishing uses only the remainder; half of what remains is relative to that remainder. Refills, spills, switches and handoffs update contents without incrementing the alcohol counter. Vessel pronouns must be the operation's grounded direct object, so accepting a handshake, rope or other object cannot reuse a prior cup merely because a later clause contains “it.” Ambiguous/replaced contents invalidate prior assumptions.

Legacy clients without prepared physical-scene context retain session/event scope. A per-turn `sceneTurnId` is not reused as a session. When a stable identity is absent, references can still resolve inside the current reply, but cannot borrow a previous turn's cup. Prepared physical scenes use the shared inventory below. The physical intoxication counter persists independently of cup expiry.

## Shared physical drink scene (2026-10-07)

`drinkSceneUpdates` records completed current service, possession, refill, transfer and discard alongside the ordinary response. It introduces no action menu, gesture requirement or additional provider request. Each observation contains `operation`, `vesselId`, `holderHeroId`, `contentsVersion`, `beverage`, `kind`, `quantity` (`unknown/full/half/quarter/empty`), `source` (`reply/player`) and an exact unique current `supportingQuote`. New local references receive deterministic server IDs and revision 1; a hidden consumption in that response can reference that local ID. Existing operations require the exact ID/revision. Contents are independently classified by the catalogue; the model cannot assert alcohol strength. Quantity requires explicit evidence; an arriving cup is not presumed full.

Observations are bounded to 16, ordered by their evidence position, and must precede the consumption they support. Present participant IDs are authoritative. Player observations can establish only the player's own completed narrated possession, never an NPC's acceptance. Plans, offers, recollections, questions, negated service, missing/nonunique quotes and unrecognized contents fail closed. A narrow compatibility recognizer covers the captured environmental “wine arrives — two clay cups” service with explicit separate possession; it establishes cups without inferring a sip. Unsupported wording needs validated observation metadata; this is not general English understanding.

`conversation_drink_scene` stores a bounded 16-vessel `reign-drink-scene-v1` inventory for the campaign's active physical scene. The anchor combines authoritative prepared venue, native settlement/location, room, party and position. Raw chat and logical-conversation IDs are excluded. Closing/reopening a chat in that scene retains cup IDs, contents and holders. Changing the physical anchor clears availability; accepting a departure prevents returning to abandoned cups. One campaign hour without accepted activity expires inventory. Missing/backward clocks do not mutate it. Unknown volume remains unknown. Without a precise prepared scene anchor the older conservative session path remains available.

Multiple participants have distinct cups. Hidden consumption selects only the speaking NPC's cup or a validated current offer; another participant's cup is unavailable. Presence alone never triggers consumption. Handoffs preserve IDs, refills increment contents revisions, discards remove availability, and narrated plus hidden consumption counts once. Recovery and intoxication counters remain independent from scene expiry. No historical missed sip is backfilled.

Preview reads do not save inventory. Final acceptance checks scene/text metadata, campaign generation, per-character state and shared inventory hash, then commits inventory, intoxication and the receipt within the same transaction as accepted dialogue effects. Concurrent participants cannot overwrite a changed inventory. Suppressed/repaired/deleted service, silent responses and rolled-back publication cannot create cups. Campaign snapshots restore inventory with counters/receipts, including on a new timeline branch.

Provider-free `drink_scene_*` contracts begin with an empty database and replay ambient wine service, the first sip, plain dialogue with hidden sipping after a new chat/logical ID, separate player custody, no automatic sip, duplicate channels, all shared route modes, final-text/metadata removal, transaction rollback, refill revision/nonalcohol, discard, invalid sources, shared-scene concurrency, physical departure, campaign-time expiry and snapshot/branch restore. Run the exact validated artifact's `conversation_intoxication` and `prompt_efficiency` suites. These prove engine behavior and schema retention; provider wording, native scene anchoring and real game save/reload still require later authorized in-game acceptance.

## Persistence, prompts and audit

The drink subsystem owns a separate **6,144 estimated input-token** allowance (`reign-drink-prompt-budget-v1`). Its rules and mandatory current intoxication/held-or-offered cup state are assembled outside the shared global prefix and live-turn allocator. A separate private message is inserted before the final player turn after core dialogue, memory and commitment context has been allocated. Existing core messages, cache hashes and allocations are preserved. Remaining space admits whole optional scene-vessel records, prioritizing the selected/available cup and this NPC's cups; omitted records remain stored but cannot be chosen in that request. Required physical state is never truncated; mandatory overflow rejects preparation. Diagnostics expose core, drink and aggregate estimates. Final provider preflight still checks the entire serialized request against actual model capacity; independence is an allocation boundary, not extra model capacity. There is no additional provider request. `drink_prompt_*` contracts in both drinking and prompt-efficiency suites exercise these boundaries, including Unicode records and aggregate rejection.

Accepted evidence also records the drinker ID, stable turn/action/occurrence event ID, vessel kind/scope and accepted consumption-event count. Cumulative `consumptionEvents` and `alcoholConsumptionEvents` are separate from `drinks`, whose unit is `gameplay_serving_equivalent`. A small pull can establish one event without establishing a full serving. An unknown bulk volume can establish an event without supplying an alcohol quantity; `alcoholVolumeMl` and `standardDrinkCount` remain null. Nonalcoholic liquid can count as consumption without increasing intoxication. Empty vessels and rejected/stale actions add no events. These fields are not visible character knowledge.

New count fields begin at `eventCountSinceHour` when first observed; existing historical state is not reconstructed. `incompleteEventCount` remains true if the engine accepts a capped amount but replaces prose so an exact action count cannot be verified. Retries reuse the same committed event receipt. The existing transaction and Save Sync snapshot restore cover counts together with state; native save/load still requires separate game acceptance.

`conversation_intoxication` stores one state row per character; its optional `vessel` object adds contents, classification, nullable remainder, session scope, hour and catalogue version. Older rows load with unknown vessel state. `conversation_drinking_turns` retains receipts keyed by hero and timeline/turn. Row locking and one transaction commit both intoxication/vessel state and its receipt. Concurrent retries return the committed reply without changing state again. Save Sync clones this same campaign schema, restoring contents and receipts alongside intoxication. No historical receipt is reprocessed and no old missed drink is backfilled.

Missing/stale clocks cannot mutate cup context or add drinks. When a proposed reply is replaced by a refusal, its unseen refill/transfer is discarded. On reaching the threshold, the accepted amount is capped and vessel context is invalidated because the replacement reaction no longer supports the proposed details. Tolerance, recovery and the restriction until below half remain unchanged. Prompt construction reads valid current context without updating storage. Private counter/volume values are not spoken as character knowledge.

State and receipt schemas remain backward-compatible `reign-conversation-intoxication-v1` and `reign-drinking-receipt-v1`. New `drinking.receipt` evidence includes occurrence span, binding, catalogue/family/classification, beverage source, quantity source/normalization, measurement quality, proposed amount, accepted amount, remaining before/after and whether proposed vessel changes were committed. An unknown bulk remainder records `unquantified_consumption` rather than making a capacity guess. Non-consumption vessel observations also emit audit evidence. Repetition cleanup preserves repeated consumption and exact occurrence metadata while reindexing surviving action paragraphs.

Recognition uses bounded English clauses, pronouns/verified speaker names, quotation masking, consumed-object matching and conservative ambiguity handling. It is not a general natural-language parser. Unsupported wording remains observable in rejected/unknown evidence; no extra provider request is made to classify a drink.

Drinks.” may inherit only this NPC's verified acquisition in the immediately preceding sentence of the same action. Another actor, a contemplated/negated acquisition or an intervening handoff does not qualify. Compound present player actions may establish an explicitly named beverage when the player retrieves/drinks and then passes that vessel to an explicit recipient. A generic “takes a drink” may refer to the currently held, unambiguous vessel. The quarter-serving fallback remains; historical receipts are unchanged. This initial repair did not retain beverage identity after relinquishment; the persistent record below now resolves grounded shared handbacks.

Native follow-up (2026-09-28): present player handoffs are evaluated within their own sentence/action, so unrelated conditional planning cannot erase an offered wine cup. Sliding or placing a vessel requires an explicit recipient/reach direction; merely moving the player's own cup, another actor's offer, quoted speech and contemplated handoffs are excluded. Comparisons such as a gesture “more of acknowledgment than drinking” establish no consumption; an independent subsequent sip still counts. These changes apply to future accepted turns and do not rewrite old drink receipts.

`ReignActionText` preserves mixed action/speech ordering and paragraphs. Balanced single `*action*` markers become only `<span style="Action">` tags. Unmatched or escaped markers stay literal. Unmarked historical prose is not reclassified. Supplied angle brackets are neutralized before native markup generation. The four chat surfaces use native `RichTextWidget`, upright `ReignSerifDynamic` and the matching genuine Cormorant Garamond Medium Italic `ReignSerifActionItalic` for actions. Brush sizes match their previous 15/16/17-pixel body roles. Player and system messages stay upright.

## Persistent shared drink and quiet consumption (2026-10-05)

The optional vessel record now includes `id`, `holder` (`npc` or `player`), `sharedWithPlayer` and `contentsVersion`. An accepted return to the player retains the vessel's identity, beverage classification and nullable remainder. A subsequent grounded return, including a short spoken invitation such as “Want another sip?”, may offer that same record. Offers alone never add consumption or change custody. An explicit new vessel, incompatible contents, third-party transfer, ambiguity, expiry or missing session invalidates old inference. The existing conversation/location and one campaign-hour limits remain. When the player drinks during a handoff, a previously measured nonzero remainder becomes unknown; player consumption is not added to this NPC's counters. Ordinary refills retain physical identity and increment `contentsVersion`.

For routine conversation the NPC may return `drinkConsumptions: [{vesselId, contentsVersion, serving, count: 1, completed: true}]` as hidden response metadata. No action menu, button, narrated gesture or asterisk paragraph is required. This is an accepted NPC choice, not inferred consumption from a player's proposal. The server requires exactly one entry, the exact currently available/held vessel and contents revision, known beverage classification, a supported portion, a nonempty vessel and no conflicting refusal. Unknown remaining volume permits only a quarter-serving sip. Known remainder caps the requested amount. Optional actor metadata cannot change the speaking NPC. Two channels describing a sip count once: accepted narrative consumption takes precedence over hidden metadata. Missing metadata never implies passive drinking between turns.

The response schemas and format repair retain the new field; failed agency repair and intoxication suppression clear it. Prepared receipts bind a consumption metadata hash and final plain speech, so changed metadata or a later refusal triggers local revalidation before the existing atomic acceptance commit. Receipt evidence adds `source=structured_consumption`, authoritative vessel ID/revision/custody and bounded quantity. Existing state/receipt schema identifiers and old receipts remain compatible; history is never backfilled. No extra provider classification call is introduced.

Inspect `drink_record_corein_*`, `drink_record_*` and `quiet_drink_*` assertions in the existing `conversation_intoxication` suite. They exercise all five captured Corein handoffs, stable identity, custody, nonalcoholic replacement, refused offers, action-free ordinary speech, strict response schemas, invalid identity/revision/amount, duplicate-channel prevention, final refusal/metadata correction, PostgreSQL snapshot restore and replay.
