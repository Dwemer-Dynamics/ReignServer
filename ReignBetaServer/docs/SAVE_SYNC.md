# Reign Save Sync

Save Sync aligns the server-owned Reign campaign state with the exact Reign snapshot registered while Bannerlord wrote a native save. It is enabled by default and can be disabled from **Campaign Backups** in the Control Center.

## Save-point identity

Each new native save serializes a Reign-generated GUID into the Bannerlord save and also records it in native save metadata. The handshake includes Bannerlord's durable campaign ID, campaign day and millisecond time, Reign world-history timeline/sequence/head, Reign capture UTC, native slot name when available, and client version. The serialized GUID is authoritative: copying or renaming a `.sav` file does not create a different Reign save point.

Before Bannerlord serializes the save, the mod gives the world-history outbox a one-second urgent flush budget and asks the server to create an immutable, immediately loadable raw generation. If critical history is still pending, the native save proceeds without waiting longer and is explicitly marked unprotected. A failed native save discards its point; an unavailable server also leaves the save unregistered. If Bannerlord successfully writes the `.sav` but Reign cannot register that snapshot, the mod opens a modal warning after serialization finishes and tells the player to start the local server and save again. Save Sync intentionally disabled does not produce this warning. On load, ordinary Reign requests wait only until the authoritative temporal generation is aligned.

Raw generation capture performs an online SQLite backup, copies changed temporal files, and uses copy-on-write hard links for immutable `profile.json` files. Hashing, inventory construction, database pruning/compaction, and content-addressed deduplication run through a single low-priority optimizer after registration returns. Optimizer failure leaves the raw generation loadable, and unfinished raw generations resume after server restart.

Save Sync retains at most 15 unique campaign states with no age limit. Identical states referenced by different native saves share one content-addressed physical snapshot and consume one slot. At 10 unique states, Bannerlord warns that only five slots remain and asks the player to delete old saves. Deleting a save through Bannerlord's native Load/Save interface deletes its matching server point after the native deletion succeeds. Successfully overwriting a named native slot also removes that slot's superseded server point. A sixteenth unique state is not registered until an old native save is deleted; the newly written Bannerlord save remains valid but is clearly reported as unprotected by Save Sync.

When deletion removes a campaign's final registered point, Reign permanently retires that campaign. An unloaded campaign is removed in the confirmed deletion transaction. A currently loaded campaign records `pending_final_save_deletion` and is removed on unload, game exit, or the next safe server startup; creating and confirming a new save first cancels retirement. Unmatched deletion notifications, imports awaiting first load, and campaigns that never registered the deleted point cannot trigger automatic retirement. Retirement covers PostgreSQL campaign and snapshot schemas, campaign files, Save Sync storage, semantic vectors, and the campaign portrait cache while preserving `_shared`. Verified staging is outside `PortraitCache`; any locked or otherwise undeleted staging is returned as residual cleanup and retried at startup.

The Control Center and Reign MCP storage audit reconcile Save Sync against the physical Bannerlord `.sav` directory. The newest Reign registration owns a reused native slot; missing and older overwritten registrations are reported as stale rather than as matching saves. Confirmed cleanup requires the exact phrase `delete Reign campaigns with no saves`, re-audits with Bannerlord stopped, removes campaigns with no matching physical save, prunes stale registrations from retained campaigns, removes verified orphan campaign/Save Sync/portrait roots, and preserves imports awaiting first load plus `_shared`. If the native save directory is unavailable, cleanup preserves every campaign.

## Storage inventory and rollback policy

| Store | Save Sync policy |
|---|---|
| `data/campaigns/<campaign>/world_memory.sqlite` | Online SQLite snapshot and whole-database restore. This covers conversations and turns, events, memories/summaries/beliefs/comprehension, relationships and developments, rumors and receipts, world history, director/action outboxes and results, rebellion/negotiation state, court/intelligence/obligations, identity/acquaintance state, reputation, character-editor queues/revisions, and semantic job metadata. |
| Campaign JSON/JSONL files | Complete directory snapshot and restore, including character histories/memories/runtime state, social-event transcripts, world history/events/memories/calendar, rumors, campaign action queue/results, diplomacy and consequences, rebellion/negotiation files, and audit files. |
| Existing-character authored/static files | Later reusable `appearance`, `background`, `characteristics`, `constructed`, `enrichment`, `profile_library`, `save_quirks`, `schema_manifest`, `template`, `traits`, and `voice` files are retained only for characters that existed at the target point. Runtime `profile`, wealth, inventory, pressure, secrets, hidden history, memory, relationship, and state documents restore from the save point. |
| Existing-character portraits | Retained as reusable assets for characters present at the target point. Characters that exist only in a future branch are not overlaid onto the target. |
| External `PortraitCache` | Intentionally retained during rollback because it is a reusable render cache. It is included in campaign export/import. |
| Native Bannerlord `.sav` files | Version-3 **Export Complete Backup** archives every physical save currently owned by the campaign. Import restores the exact hash-verified files into Bannerlord's native save directory, making the bundle portable and load-ready for diagnostics on another computer. A different local save with the same filename is never overwritten without the separate **Replace conflicting native Bannerlord save files** confirmation. |
| Campaign technical audit | Retained for diagnostics and never used as prompt or gameplay memory. Save Sync also writes a separate append-only audit beside the external Save Sync ledger. |
| Semantic vector provider | A divergent load blocks semantic retrieval for that campaign, atomically installs authoritative temporal state, and immediately falls back to SQLite lexical search. Vector invalidation and restored-row reindexing then run in the background; semantic retrieval reopens only after reconciliation finishes. |
| Client world-history outbox | Rewritten to the loaded timeline and saved sequence before any upload can resume, preventing queued events from the abandoned future from being re-ingested. |
| Global settings, API keys, prompts, logs, and profile catalog | Not campaign temporal state and never rolled back or placed in campaign exports. |

## Atomicity, recovery, and audit

Ordinary HTTP campaign work shares a reader/writer gate with Save Sync. SQLite is copied with the online backup API. A durable active-generation marker makes loading the already-active save point an immediate no-op. Before a divergent install the server creates a raw recovery snapshot under the compact `data/ss/<campaign-key>/r/` store; two recovery snapshots are retained. Full campaign and save-point IDs remain in the ledger, while optimized content-addressed directories allow multiple point identities to share identical data. Short SHA-256-derived directory keys keep deep Bannerlord paths below Windows legacy path limits. Hash-key mismatches are rejected. The target is prepared in staging, the active directory and stage are swapped on the same volume, and any exception restores the original directory. Failed synchronization never opens the client request barrier.

The external ledger at `data/ss/<campaign-key>/ledger.json` records registered points, last loaded point, last result, duration, changed files, per-subsystem record deltas, recovery backup ID, and errors; adjacent `audit.jsonl` preserves technical history. The Campaign Backups UI exposes those fields and supports a non-mutating preview.

## Compatibility and migration

The format-4 migration intentionally removes all legacy format-3 snapshot content and ledger points, including snapshots containing the historical duplicated `actionResolutionIndex` payload bug. Format-5 keeps format-4 points fully load-compatible and adds raw-generation/background-optimization state. Active campaign data is not deleted. Existing pre-Save-Sync Bannerlord saves without a serialized point GUID can still establish a deterministic legacy baseline from campaign ID, campaign time, timeline, history sequence/head, and main hero, but purged registered points cannot reconstruct their former Reign history. Campaign `.reignbackup` version 3 archives include the current ledger, raw or optimized snapshots, recovery metadata, Save Sync audit, portrait cache, and every matching physical native save. Version-2 archives remain import-compatible but do not contain a native save, so the recipient must supply that matching `.sav` before the imported campaign can be loaded.
